# gfx1201 plain-codebook (cb0) GEMV: implementation record

Status: implemented and validated on 2026-11-03 on `gfx1201`. Commits: `4d2a390` (cb0 route), `5a24df6` (findings/oracle), `23375e4` (skinny hgemm fix), `b903c7a` (docs), `95c8827` (RDNA fdot2 m=1 GEMV).

## What was done

- Added ROCm `cb=0` GEMV instantiations for K2/K3/K5/K6 in
  `exllamav3/exllamav3_ext/quant/exl3_gemv.cu`: `SEL_GRID(2,0)`, `(3,0)`, `(5,0)`,
  `(6,0)` (MMODE 0/1, CFG 0/1, fp16/fp32 output). No MMODE-2 instantiations.
- Relaxed the two `K != 4 && cb == 0` guards under `#if !defined(USE_ROCM)`; the CUDA
  branch and its K 2..4 limits are unchanged.
- `exllamav3/modules/quant/exl3.py:515`: plain K2..6 now routes to `hip_gemv`.
  Half-integer bitrates still require mul1, matching the kernel gate.
- Tests: K2/K3/K5/K6 plain synthetic oracle, all-K procedural-codebook zero-state,
  K5-plain accepted case, real Ora K2/K3/K5 tensors, oracle `EXL3_ORACLE_STEPS` and
  free mode, strict Ora route proof.
- Added `tools/strix_halo/coherence_suite.py` (8 prompts x greedy/default, loop guard,
  20-gram repeat, EOS).
- Fixed a pre-existing ROCm skinny hgemm grid bug (m=9..32, n<=128 left columns
  64..127 unwritten; see below).
- Docs: `doc/roc_hip_decode.md`, `README.md`, `README.strix-halo.md`, this file.

## Bugs found and fixed during this work

### ROCm skinny hgemm left columns 64..127 unwritten for m=9..32, n<=128

The ROCm `hgemm` skinny path (`hgemm.cu`, m<=32, n<=128) chooses two adjacent
columns per lane (`CPL=2`) when `n` is even and >=64. For m>8 it then dispatches the
padded one-column instantiations with the *CPL=2 grid*, so `grid.x` was half of what
the one-column kernel covers: at n=128 only columns 0..63 were written. Because
`LinearEXL3.reconstruct_hgemm` passes `torch.empty`, the unwritten half kept
allocator garbage, making the reconstruct fallback nondeterministic for rows 9..32
(observed: repeated calls differed by O(1); with C zero-filled, C stayed zero in the
upper half).

Fix (`hgemm.cu`): restrict `CPL=2` to `m <= EXACT_M` (8), so rows 9..32 always use
the one-column path with a matching grid. Verified: all 128 columns written at
m=9/n=128, n=256 rows 9-16 match, and the previously failing MMODE-2/K5 synthetic
tests pass at n=128. This is independent of the cb0 GEMV route, but it removed the
false "MMODE-2 narrow is broken" signal (the GEMV at n=128 is bit-identical to
`reconstruct + torch.matmul`).

`test_hip_gemv_mmode2_narrow_n_matches_matmul` keeps an independent matmul-reference
oracle for the n=128 MMODE-2 cell.

## RDNA fdot2 GEMV for m = 1

The generic gfx12 GEMV kernel (`quant/exl3_gemv_kernel.cuh`) is built on
`m16n8k16` WMMA. Upstream exllamav3 v1.6.6 reaches 89.8 tok/s on the same pack
with a different ROCm kernel: `rocm/quant/exl3_gemv_rdna.cu`, a one-warp-per-16-
output-tile GEMV whose inner product is `V_DOT2_F32_F16` and whose trellis decode
is the hand-laid "tiles" core. That kernel is now ported as
`exllamav3/exllamav3_ext/rocm/quant/exl3_gemv_*.cuh` / `.cu`.

Routing (`quant/exl3_gemv.cu`):

- only `m == 1`, integer K (no half-integer mul1), `gfx1200`/`gfx1201`;
  rows 2..16 keep the existing WMMA path, so the gfx1151 route is unchanged;
- the input Hadamard is still the caller's `had_r_128`; the dot kernel fuses the
  output Hadamard into its store when `size_n / 128 <= 1024` (all dense
  projections; the 248,320-wide lm_head keeps a separate output launch);
- the RDNA kernel replaces only the middle launch of the three-launch form, so
  the output contract and the Python route (`LinearEXL3.hip_gemv`) are unchanged.

### Experiments measured and dropped

- **Gate/up pair kernel** (one rotation launch for both matrices, one dot launch,
  `grid.y = 2`): outputs are identical to two `hip_gemv` calls (greedy token IDs
  match), but the end-to-end win was 1.5-1.7%, below the >3% keep threshold, and
  the two matrices have different `suh`, so the rotation cannot be shared.
- **One-launch fused kernel** (input rotation in the dot kernel's LDS prologue,
  output in the store): 72.7 tok/s, worse than the two-launch form; the LDS
  prologue costs more occupancy than the saved launch.
- **Whole-model HIP graph** (`EXL3_CUDA_GRAPH=1` with the CUDA-only gate
  relaxed): 82.7-84.9 tok/s, but the independent coherence suite failed
  intermittently on long-form/instruction prompts that pass eagerly. The graph
  runner was written for the CUDA BC blocks and bakes host-side GDN branch
  decisions into the capture. Reverted; the engine's default stays eager.

### Remaining gap to upstream

At 76.8-77.5 tok/s the engine is at ~86% of upstream's 89.8 on the same pack and
device. The dot kernel is at parity, so the remaining ~1.5 ms/token is outside
it: upstream runs whole blocks through its C++ `BC_*` graph modules
(`libtorch/*_hip.cpp`), while this tree still runs the dense Python modules
eagerly. A `process_time` measurement during decode is ~14.6 ms CPU/token versus
~12.9 ms wall, i.e. the host side is saturated. Closing the gap needs either a
port of the BC block stack or a graph-safe dense-block path; not another GEMV
config.

## Findings that need follow-up

1. **Upstream gap (perf).** 76.8-77.5 vs 89.8 tok/s after the RDNA fdot2 port.
   The m=1 dot kernel is now at upstream parity (10.2-10.3 ms per 201-linear
   streaming pass vs 9.93 ms); the residual gap is host-side/BC-block fusion, not
   the GEMV. See "RDNA fdot2 GEMV for m = 1" above.
2. **Pre-existing test failures, reproduced on the pristine baseline `.so`:**
   `test_hip_routing_std_gfx12` kernel-name profiling (ROCm profiler exposes no device
   kernel names), `test_hip_block_graph` rows-decline counter, and
   `test_hip_grouped_moe_k3` (`ext.exl3_moe_gfx12_k3` TypeError, 89 cases).
3. **Multi-device JIT arch.** `vendor/fla/hip/gdn_hf_hip.py`,
   `gdn_fused_h_hip.py`, and the `gr_mix` compile path still take device 0's
   `gcnArchName`; `hip_compiler.py` has no device argument. Default-off on family 1,
   but unsafe if enabled with the dGPU at a nonzero index.
4. **Fixture availability.** Qwen3.8-27B and the 9B MCG fixture are not on the halo
   (`/data/models` has Ora, Flash-Next, GLM-5.3 only). Their acceptance-matrix rows are
   coverage only; no downloads were triggered.
5. **gfx11.5-only kernels.** `exl3_dec`, `qdec.hip`, `gr_mix` stay pinned to family 2;
   quantized KV on gfx1201 still falls back to Triton (correct, slow).
