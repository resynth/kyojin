# gfx1201 plain-codebook (cb0) GEMV: implementation record

Status: implemented and validated on 2026-11-03 at `4d2a390` (`gfx1201` branch).

## What was done

- Added ROCm `cb=0` GEMV instantiations for K2/K3/K5/K6 in
  `exllamav3/exllamav3_ext/quant/exl3_gemv.cu`: `SEL_GRID(2,0)`, `(3,0)`, `(5,0)`,
  `(6,0)` (MMODE 0/1, CFG 0/1, fp16/fp32 output). No MMODE-2 instantiations.
- Relaxed the two `K != 4 && cb == 0` guards under `#if !defined(USE_ROCM)`; the CUDA
  branch and its K 2..4 limits are unchanged.
- `exllamav3/modules/quant/exl3.py:515`: plain K2..6 now routes to `hip_gemv`.
  Half-integer bitrates still require mul1, matching the kernel gate.
- Tests: K2/K3/K5/K6 plain synthetic oracle, all-K procedural-codebook zero-state,
  K5-plain accepted case, real Ora K2/K3/K5 tensors, oracle `EXL3_ORACLE_STEPS` and
  free mode, strict Ora route proof.
- Added `tools/strix_halo/coherence_suite.py` (8 prompts x greedy/default, loop guard,
  20-gram repeat, EOS).
- Docs: `doc/roc_hip_decode.md`, `README.md`, `README.strix-halo.md`.

## Measurements

Environment: `/opt/rocm` 7.15 (HIP 7.15.26333), torch 2.15.0+rocm10.0, fat extension
built with `PYTORCH_ROCM_ARCH="gfx1201;gfx1151"`, `EXL3_HIP_STG_PAD`. Pack:
`/data/models/Qwen3.5-9B-Ora` (plain cb0; K2 124 tensors, K3 61, K4 15, K5 lm_head).

| Run | All-reconstruct | Plain-codebook GEMV |
| --- | ---: | ---: |
| RX 9070 (gfx1201), 128 tok, 3 trials | 16.85-16.89 tok/s | 57.65-58.33 tok/s |
| 8060S (gfx1151), 64 tok, 3 trials | 5.06-5.10 tok/s | 37.29-37.47 tok/s |

Both baselines were rebuilt from pristine `4e82eaf` with the same recipe, not taken
from the plan's earlier `.so`. Uplift: 3.45x on gfx1201, 7.35x on gfx1151.

Same pack on upstream exllamav3 v1.6.6 (its `BC_LinearEXL3` HIP path), same device and
prompt: 89.76 tok/s. The cb0 GEMV path reaches 65% of that.

Route census (32-token decode): 6,629 `exl3_gemv` calls, zero
`reconstruct`/`reconstruct_slice`; about 207 GEMV launches per token. Before the
change the same run made 6,102 `reconstruct` calls.

Per-shape microbenchmark at m=1: 110-155 GB/s on dense shapes up to 4096x12288;
K5 lm_head (4096x248320) reaches 356 GB/s. A forced cfg 0/1 sweep (temporary
`EXL3_GEMV_CFG` hook, removed) stayed within run-to-run drift (<3%), except the
already-selected wide config on gate/up; the heuristic was left unchanged.

## Oracle

Qwen3.5-9B-Ora, forced-token logits, reconstruct arm vs GEMV arm:

| Steps | top1 | top5 min | max delta | worst-step mean | overall mean |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 16 | 16/16 | 4/5 | 0.039063 | 0.006269 | 0.003372 |
| 128 | 128/128 | 3/5 | 10.248047 | 1.204178 | 0.077248 |
| 128 (gfx1151) | 128/128 | 2/5 | 9.047852 | 1.139217 | 0.085564 |

The 128-step deltas grow on both devices because the hybrid GDN cache state is fed by
the numerically different linears; this is the fixture, not a gfx12 path bug. Forced
top-1 identity is the hard signal and stays 128/128. The oracle therefore keeps the
tight bounds through 32 steps and uses trace-length-scaled delta bounds above that.

## Quality

`coherence_suite.py` on both devices: 8 prompts x {greedy, default} = 16 runs each,
all reached EOS, zero loop-guard fires, no 20-gram repeated more than twice. The
raw-completion loop seen with `load_qwen.py` (free mode token ids repeat an 8-token
cycle) does not reproduce through the chat template; `tools/qwen/serve.py` remains the
supported chat path.

## Findings that need follow-up

1. **Upstream gap (perf).** 58.2 vs 89.8 tok/s on the same pack/device. The small-N
   GEMVs are latency/occupancy-bound on 128 CUs (110-155 GB/s), not launch-bound.
   A split-K or finer-N gfx12 config is the likely lever. `cfg 0/1` and multi-weight
   fusion alone were not justified by the measurements.
2. **The reconstruct oracle is nondeterministic at m>8, n<=128 (pre-existing).**
   `hgemm` on ROCm takes the skinny path for m<=32, n<=128; at m=9, n=128 its output
   varies run to run (C is not fully/atomically written for rows 9..32).
   `LinearEXL3.forward`'s reconstruct fallback passes `torch.empty`, so repeated calls
   differ by O(1). This made the old MMODE-2 synthetic tests fail; it is not a GEMV bug:
   the GEMV at n=128 is bit-identical to an explicit `reconstruct + torch.matmul`
   reference (`test_hip_gemv_mmode2_narrow_n_matches_matmul`). The MMODE-2 reconstruct
   oracle tests now use n=256; the n=128 case uses the matmul reference.
   Follow-up: fix the skinny hgemm C write/accumulation contract (affects every
   reconstruct of an n<=128 projection at rows 9..32).
3. **MMODE-2 synthetic coverage** moved from n=128 to n=256 for the reconstruct oracle;
   the n=128 case is covered by the matmul-reference test. No kernel or route change.
4. **Pre-existing test failures, reproduced on the pristine baseline `.so`:**
   `test_hip_routing_std_gfx12` kernel-name profiling (ROCm profiler exposes no device
   kernel names), `test_hip_block_graph` rows-decline counter, and
   `test_hip_grouped_moe_k3` (`ext.exl3_moe_gfx12_k3` TypeError, 89 cases).
5. **Multi-device JIT arch.** `vendor/fla/hip/gdn_hf_hip.py`,
   `gdn_fused_h_hip.py`, and the `gr_mix` compile path still take device 0's
   `gcnArchName`. They are default-off on family 1, so gfx12 inference is unaffected,
   but they are unsafe if enabled with the dGPU at a nonzero index.
6. **Fixture availability.** Qwen3.8-27B and the 9B MCG fixture are not on the halo
   (`/data/models` has Ora, Flash-Next, GLM-5.3 only). Their acceptance-matrix rows are
   coverage only; no downloads were triggered.
7. **gfx11.5-only kernels.** `exl3_dec`, `qdec.hip`, `gr_mix` stay pinned to family 2;
   quantized KV on gfx1201 still falls back to Triton. Correct but slow.

## Repro

Build (halo, build shell):

```bash
cd /home/m/engines/kyojin
export EXL3_ROOT=$PWD EXL3_VENV=/home/m/engines/exllamav3/.venv EXL3_ROCM_SDK=/opt/rocm
source tools/strix_halo/env.sh build
export PYTORCH_ROCM_ARCH="gfx1201;gfx1151" MAX_JOBS=4 EXL3_HIP_DEFINES=EXL3_HIP_STG_PAD
/home/m/.local/bin/uv pip install --python "$EXL3_VENV/bin/python" \
    --no-build-isolation --no-deps --target /tmp/site "$PWD"
cp /tmp/site/exllamav3_ext*.so "$PWD"/
```

Run (runtime shell):

```bash
HIP_VISIBLE_DEVICES=1 python tools/strix_halo/load_qwen.py -m /data/models/Qwen3.5-9B-Ora -n 128
HIP_VISIBLE_DEVICES=1 EXL3_TEST_MODEL=/data/models/Qwen3.5-9B-Ora EXL3_ORACLE_STEPS=128 \
    python tests/hip_gemv_logits_oracle.py
HIP_VISIBLE_DEVICES=1 EXL3_TEST_MODEL=/data/models/Qwen3.5-9B-Ora \
    python -m pytest -q tests/test_hip_gemv_decode.py \
    -k "synthetic_oracle or procedural or k5_plain or plain_codebook_real_weight"
HIP_VISIBLE_DEVICES=1 python tools/strix_halo/coherence_suite.py -m /data/models/Qwen3.5-9B-Ora -n 192
```
